# 运行时配置热更新设计

## 目标

用户在 Web 设置页编辑一个或多个配置项时，内容只保留在浏览器草稿中；用户点击全局“保存并应用”后，配置一次性落盘，并让后续新建的聊天、分析、指数分析和推送任务使用新配置。已经开始的任务继续使用其启动时取得的运行时依赖，不被中途替换。

`api.host` 与 `api.port` 是例外：它们对应 Uvicorn 已经绑定的监听套接字，只能保存并提示用户重启 `stock-robot run`。

## 当前状态与问题

配置 API 在 `src/api/configuration.py` 每次请求重新创建 `Config`，因此可以把修改写入 `.stock_robot/config.yaml`。但是 API 服务启动时由 `build_agent_core()` 构建一份 `AgentCore`，其中的 LLM 后端、`Pipeline`、工具注册表和聊天模型都引用启动时的 `Config`。`PushExecutor` 和 `PushScheduler` 也分别持有启动时的 `core` 与 `config`。

因此当前“保存成功”仅代表写盘成功。除信号计算、订阅数量限制等每次请求重新创建 `Config` 的调用点外，多数运行中依赖并不会应用新值；设置页目前只为 host/port 给出重启提示，语义不完整。

## 设计原则

1. **先构建、后切换。** 新运行时构建失败时，已运行服务继续使用旧运行时；API 返回可读错误，不写入半成品运行时。
2. **任务使用快照。** 每个请求在开始阶段读取一次当前快照并持有到结束；配置切换不会影响正在执行的 SSE、聊天、分析或推送任务。
3. **单次提交。** 浏览器只在用户显式点击全局保存按钮时请求 `PUT /api/v1/config`；输入事件绝不写盘。
4. **原子可见。** 新任务只能看见完整旧快照或完整新快照，不能取得新 LLM 配置和旧工具注册表的混合状态。
5. **最小重启范围。** host/port 保持“保存后重启生效”；所有其他受控字段在新任务中热更新。

## 运行时架构

新增一个由 API 启动路径创建的 `RuntimeManager`。它持有当前的不可变运行时快照：

```text
RuntimeSnapshot
├── config: Config
├── core: AgentCore
├── push_executor: PushExecutor
└── push_scheduler: PushScheduler
```

容器公开以下职责：

- `snapshot()`：以短临界区读取当前快照；调用者随后在锁外使用快照。
- `reload(config)`：在锁外基于已校验配置构建新的 `AgentCore` 与 `PushExecutor`；构建成功后在锁内替换当前快照。
- `apply_push_state()`：根据新 `push.enabled` 启动、停止或重载调度器；不会终止已经触发的推送任务。

`RuntimeManager.reload(config)` 先以同一个 `Config` 实例构建新 `AgentCore`、`PushExecutor` 与 `PushScheduler`，再替换 `RuntimeSnapshot`。替换完成后关闭旧 `PushScheduler`，并启动新调度器；旧调度器已经派发的任务继续持有旧执行器和旧核心直到结束。

切换由线程锁保护。构建 LLM 客户端、注册工具等可能耗时或失败的操作必须在锁外完成；只有引用替换需要持锁。旧快照被已经运行的请求持有，完成后由 Python 引用计数/垃圾回收释放。

`create_app()` 不再将闭包中固定的 `core` 直接用于请求处理，而是接收或创建运行时容器；聊天、SSE、工具列表、手动触发推送等入口先取得一次快照。`_build_agent()`、`ReActExecutor`、`PushExecutor.run_subscription()` 都使用调用开始时获取到的同一份快照。

## 配置保存与热更新流程

```text
浏览器本地草稿
  └─ 点击“保存并应用”
       └─ PUT /api/v1/config
            ├─ 校验白名单、类型与阈值关系
            ├─ 写入 config.yaml（一次）
            ├─ host/port：标记 restart_required，不变更监听器
            ├─ 非监听配置：构建并原子替换 RuntimeSnapshot
            └─ 返回 applied / restart_required / 配置展示值
```

配置已落盘但热重载构建失败时，接口须返回明确错误，并保留旧快照继续服务。实施时应避免“写入成功、返回 500、用户不知道是否已保存”的歧义：响应需要包含 `persisted` 和 `applied` 两个独立状态，前端据此提示“已保存，尚未应用；请修正配置后再次保存或重启”。

仅涉及 host/port 的保存返回 `persisted=true, applied=false, restart_required=true`。包含 host/port 与其他热更新字段时，其他字段仍然应用；响应保持 `restart_required=true`，前端同时说明监听地址/端口需重启。

## 设置页交互

设置页只维护本地草稿，现有 `changed` 集合继续作为脏状态来源。

- 初始加载、保存成功或刷新配置后：没有提示条，也没有待保存草稿。
- 用户编辑任意字段：显示位于设置内容顶部的粘性提示条（`position: sticky`），文案为“有 N 项配置尚未保存”。
- 提示条提供唯一的“保存并应用”按钮；移除页面底部重复的保存入口。
- 点击按钮前：不发出配置更新请求，不修改 YAML，也不影响运行时。
- 保存请求期间：禁用按钮并显示进行中状态，避免重复提交。
- 保存成功：重新读取安全配置、清空草稿、隐藏提示条；根据响应显示“已保存并应用”或“已保存，监听地址/端口重启后生效”。
- 保存失败：保留全部输入内容和 `changed` 状态，保持提示条可见，并显示后端错误。
- 切换到其他视图：草稿只保存在当前页面内存中，不写盘；浏览器刷新、重新加载设置页或服务重启时丢弃草稿。这是“未保存不修改”的明确边界。

密钥继续遵循现有展示规则：默认只显示掩码占位符；输入新密钥也只是前端草稿；睁眼只读取当前已保存的密钥，不会读取尚未提交的替换值。用户点击保存后才将新密钥提交到本机 API。

## 字段生效矩阵

| 字段类别 | 保存后行为 |
| --- | --- |
| `api.host`、`api.port` | 写入配置文件，必须重启服务 |
| `llm.*` | 重建 LLM 后端、聊天模型和 AgentCore；后续聊天/分析生效 |
| `data.cache_ttl.*` | 重建 Pipeline；后续缓存写入使用新 TTL |
| `push.enabled` | 启动或停止后续调度；不取消已开始推送 |
| `push.email.*`、`push.wecom.*` | 重建 PushExecutor；后续推送使用新渠道配置 |
| `push.max_symbols_per_subscription` | 后续订阅创建/修改立即使用新上限 |
| `signal.*` | 后续报告与推送生成使用新阈值和文案 |
| `data.disclaimer_accepted` | 写入后供后续读取配置的流程使用 |

## 错误处理与可观测性

- 热重载构建阶段捕获第三方 SDK 初始化错误，记录包含配置类别但不含密钥的日志。
- 返回客户端的错误不得包含 API Key、SMTP 密码、企业微信 Secret 或完整配置 YAML。
- 重载成功、失败、调度器启动/停止、监听配置待重启都应写入 INFO/WARNING 日志，便于排查用户所见状态。
- 热重载不会监听文件系统变化；命令行直接编辑 YAML 后，必须通过设置页保存一次或重启服务。这样避免外部文件写入造成无验证的运行时切换。

## 测试与验收

1. 单元测试：运行时容器成功替换快照；构建失败保留旧快照；并发读取只获得完整快照。
2. API 测试：非监听配置保存后返回 `persisted/applied`；监听配置返回 `restart_required`；混合更新同时应用可热更新字段并标记重启。
3. 行为测试：正在执行的聊天/推送持有旧快照，新请求使用新快照。
4. 推送测试：开关改变后调度器正确启动、停止或重载，已开始任务不被终止。
5. 前端静态契约测试：编辑不触发 PUT；提示条在变更后出现并显示计数；保存成功隐藏；失败保留草稿；密钥仍只在点击保存时提交。
6. 真实 Web 验收：通过 `.venv/Scripts/stock-robot.exe run` 启动，修改一个可热更新项、保存、发起新请求验证其使用新快照；另修改端口验证页面提示重启而服务不迁移监听端口。

## 非目标

- 不支持 `api.host` / `api.port` 无中断迁移。
- 不对已经运行的分析、SSE 或推送任务强制注入新配置。
- 不将未保存草稿写入 localStorage、会话数据库或服务端。
- 不增加配置文件监听器或从磁盘变更自动热更新。
