# AstrBot 插件自动启动服务（含依赖拆分）设计

日期：2026-09-28
承接：`2026-09-18-astrbot插件接入设计.md`（该 spec 第 29 行把"插件懒启动服务"列为 P1 备选，本设计把它提为当期工作，并按 P1 备注的代价逐项处理）

## 背景与目标

现状：插件（`D:\code\astrbot_plugin_stock_robot`）已通过 QQ 实测，可用，但要求用户**自己先把 stock_robot 服务跑起来**（`stock-robot run`），否则所有工具调用都回"分析服务未启动"。

目标：**用户只启动 AstrBot，插件自己把分析服务准备好。**

- 零配置优先：正常情况下用户不填任何路径
- 已有服务在跑 → 直接复用，不重复启动、不误杀
- 本机已有安装 → 找到并启动它（保留用户既有配置与报告历史）
- 都没有 → **自举**：clone 上游仓库、建独立环境、装依赖、写最小配置、启动
- 只为"自用 + 预留发布"服务，不追求多用户/多实例管理

## 非目标（本期不做）

- 不做自动升级（`instance/` 已存在即跳过 clone 与安装）
- 不做进程守护/崩溃自动重启（调用期兜底已覆盖"挂了再拉起来"）
- 不做 Windows 服务化、开机自启
- 不新增主仓 HTTP 端点；主仓只做依赖拆分与一处 `rag` 子命令的友好提示（见"主仓改造"）
- 不为发布做 GitHub 打包/插件市场提交（沿用上一份 spec 的发布预留章节）

## 决策记录

| 问题 | 结论 | 理由 |
|---|---|---|
| 启动命令从哪来 | 插件拼 `run --host <base_url 的 host> --port <端口>`，只暴露 `startup_port` | 用户选择"不填命令、少填配置"；端口与 base_url 不会不一致 |
| 位置知识来源 | **探测优先（PATH + 可选 `install_path`）→ 失败则自举** | 用户选择；自用机器大概率走探测，自举只在"新机器/没找到"时触发 |
| 进程生命周期 | **只关自己拉起的** | 复用用户手动启动的实例，避免误杀 |
| 触发时机 | **插件启用时启动 + 调用时兜底** | 启用即就绪；中途挂了/启动失败还能自愈 |
| 自举的 LLM Key | **从 AstrBot 当前 provider 自动写入** | 这是"零配置"的关键；代价是 Key 明文落到插件数据目录（与主仓现有做法一致） |
| 自举触发时机 | 只在**插件启用**时触发，调用时只等待进行中的启动 | 避免"问一句股票就卡 10 分钟装依赖" |
| 依赖拆分 | **只拆 rag**（chromadb + sentence-transformers） | torch 那 2~3 GB 是 rag 独占；vectorbt/apscheduler 体积小，拆分收益不值当 |
| RAG 依赖的地位 | 移入 `[project.optional-dependencies] rag` | 插件的三个端点（analyze/index/reports）完全不用 RAG；主仓已有 try/except 守卫，代码零改动 |

### 服务来源解析链（`resolve()`，第一个成功即止）

| 级别 | 条件 | 动作 |
|---|---|---|
| 0 | `base_url` 主机不属于本机（非 `127.0.0.1`/`localhost`/`::1`） | **短路**：只做级别 1，不做 2/3（远程服务无从启动） |
| 1 | `GET {base_url}/health` 通 | 复用。不启动、不记 `_owns_process` |
| 2 | 存在配置的 `install_path`，或遍历 PATH 找到可校验的安装 | 启动它，`cwd=项目根`，记 `_owns_process` |
| 3 | `auto_install` 为真 | 自举到 `{plugin_data}/astrbot_plugin_stock_robot/instance/`，启动，`cwd=instance` |
| 4 | 以上都失败 | 保留失败原因，调用时回现状错误消息 |

### 级别 2 的校验规则

- 候选来源：先看配置 `install_path`（填了就以它为准），再遍历 PATH **全部条目**（不是只取 `shutil.which` 的第一个）找 `stock-robot` / `stock-robot.exe`
- 对每个候选：
  - 命中路径形如 `<root>/.venv/Scripts/stock-robot.exe`（Windows）或 `<root>/.venv/bin/stock-robot`（POSIX）→ `root = 上溯三级`
  - 否则（例如用户级 shim `<python>/Scripts/stock-robot.exe`）→ **无法推导项目根 → 跳过**（本机 Anaconda 那份会走到这里被跳过）
- 校验 `root` 下存在 `.stock_robot/`（已配置过的安装）或 `pyproject.toml` 中 `name = "stock-robot"`
- 校验通过 → 用该 `root/.venv` 里的可执行文件启动，`cwd=root`

> **本机注意**：级别 2 在你这台机器上默认**找不到**（`.venv\Scripts` 不在 PATH）。所以配置项 `install_path` 建议填 `D:\code\stock_robot`——否则不填就会走级别 3，多装一份副本。

## 组件与接口

新增两个模块，均**不依赖 astrbot**，可独立单测（与既有 `client.py` 同样的边界）。

### `launcher.py`

```python
@dataclass
class Plan:
    kind: Literal["reuse", "launch", "bootstrap", "none"]
    executable: Path | None      # launch / bootstrap 用
    cwd: Path | None
    reason: str                  # none/bootstrap 时的诊断原因

class ServiceLauncher:
    def __init__(self, base_url, port, install_path, executable_hint, timeout, ...): ...
    async def resolve(self) -> Plan                      # 级别 0~3
    async def ensure_ready(self, allow_install: bool) -> ReadyOutcome
    async def stop(self) -> None                          # 只结束自己拉起的
    @property
    def state(self) -> Literal["idle", "starting", "ready", "failed"]
```

- `ensure_ready` 内部用 `asyncio.Lock` 做**单飞**：并发调用共享同一次启动等待，绝不拉起第二个进程
- `state == "failed"` 时保留失败原因（`ReadyOutcome.reason`），调用期直接复用而不重试安装
- 子进程 stdout/stderr 追加写入 `{plugin_data}/astrbot_plugin_stock_robot/service.log`

### `bootstrap.py`

四个独立步骤，各自可单测、可返回明确失败原因：

1. `clone(repo_url, dest)` — `git clone --depth 1 <url> <dest>`；目标已存在则跳过
2. `make_env(dest, extras)` — 优先 `uv venv` + `uv pip install`，回退 `sys.executable -m venv` + `pip install`；安装 `-e ".[{extras}]"`（`extras` 为空则 `-e .`）
3. `write_config(dest, provider, port)` — 写 `{dest}/.stock_robot/config.yaml`：`llm` 段取 AstrBot 当前 provider 的 `provider/model/api_key/base_url`，其余用主仓默认值，`api.port = port`
4. `ensure_instance(...)` — 编排 1~3 + 就绪等待；失败用 `logger.warning` 记录原因摘要（插件启用时没有会话上下文，进度只能看 AstrBot 日志页）

### `main.py` 挂钩

| 位置 | 动作 |
|---|---|
| `initialize()` | `asyncio.create_task(launcher.ensure_ready(allow_install=True))`，立即返回，不阻塞插件加载 |
| `_run_analysis()` 入口 | `await launcher.ensure_ready(allow_install=False)`；失败不打断流程，交给 `client` 现有错误路径 |
| `terminate()` | `await launcher.stop()` + 现有 `client.aclose()` |

## 配置项（`_conf_schema.json` 新增 6 项）

| 配置 | 默认 | 说明 |
|---|---|---|
| `startup_port` | 空 → 取 `base_url` 的端口 | 自动启动时监听端口 |
| `startup_timeout_seconds` | 60 | 等服务就绪上限（**不含**自举安装耗时） |
| `install_path` | 空 → 只走 PATH 探测 | stock_robot 项目根，自用建议填 `D:\code\stock_robot`（不填则本机大概率落到自举，多装一份副本）。填了优先用它，校验不过则回退 PATH 探测 |
| `auto_install` | `true` | 关闭则只在"已跑 / 已有安装"里找，绝不 clone 不装依赖 |
| `bootstrap_extras` | 空 | 自举时装的可选依赖；可选 `rag`（chromadb + sentence-transformers，含 torch，数 GB） |
| `source_repo_url` | 空 → 内置常量 `https://github.com/Arrhenius401/stock_robot.git` | 自举源；私有仓库或镜像时填（可含 token） |

## 触发规则与时序

### 插件启用（`initialize`）

1. 立即创建后台任务并返回
2. 后台：`resolve()` → 级别 1 命中则结束；否则级别 2 启动；否则级别 3 自举
3. 自举过程中每次用户提问（工具调用）会走到 `ensure_ready(allow_install=False)`，看到 `state == "starting"` → 等待（最多 `startup_timeout_seconds`），仍不就绪则回错误消息并提示"服务可能在安装中，详见插件日志"

### 工具调用

1. `state == "ready"` → 直接走分析流程（现状不变）
2. `state == "starting"` → 等待进行中的启动
3. `state in ("idle", "failed")` → 先补一次 `resolve()`：级别 1/2 允许启动（秒级）；只剩级别 3 且有 `auto_install` → **不在调用时安装**，直接回错误
4. 失败消息：现有 `❌ 分析服务未启动（{base_url}），请先运行 stock-robot run` 基础上追加一句诊断（安装中 / 安装失败原因摘要 / 日志路径）

### 插件禁用 / 重载（`terminate`）

- 只结束 `_owns_process` 为真的子进程（`terminate()` → 超时 5s 后 `kill()`）
- 重载 = 杀自己那份 + 重新解析（若用户手动启动的实例在跑，级别 1 会复用，不受影响）

## 自举细节

- 家目录：`{plugin_data}/astrbot_plugin_stock_robot/instance/`，它同时是 `cwd` → 生成 `instance/.stock_robot/config.yaml` 与 `instance/reports/`
- 幂等：`instance/` 存在即跳过步骤 1~3，只启动
- LLM Key：从 AstrBot 当前生效 provider 读取，写入 `instance/.stock_robot/config.yaml`（明文，与主仓现状一致）
- 依赖：默认核心依赖（含 vectorbt、apscheduler），不含 `rag`；`bootstrap_extras=rag` 时才装 RAG
- 耗时预期：核心依赖首次安装数分钟；失败时保留 pip 输出的最后若干行作为原因摘要

   - 从 `dependencies` 移除 `chromadb>=0.5`、`sentence-transformers>=3.0`

## 错误处理

| 场景 | 处理 | 用户可见 |
|---|---|---|
| `base_url` 非本机 | 只做级别 1 | 现状消息 |
| PATH 候选无法推导项目根 | 静默跳过（`logger.debug`），继续下一个 | 无 |
| `install_path` 指向无效目录 | `logger.warning`，回退到 PATH 探测 | 无（探测到才启动） |
| clone 失败（网络/权限） | 记录输出尾部 | "分析服务安装失败：{摘要}（详见插件日志）" |
| 建环境 / 装依赖失败 | 记录 pip/uv 输出尾部 | 同上 |
| 子进程立即退出（端口占用等） | 读 stderr 尾部 | "分析服务启动失败：{stderr 尾部一行}" |
| 就绪超时 | 记 `startup_timeout_seconds` 与日志路径 | "分析服务启动超时（{n} 秒），详见插件日志" |
| 调用期不触发安装 | 不在调用时 clone/装依赖 | "分析服务未就绪（可能在安装中），详见插件日志" |
| 全失败 | 保留原因 | 现状"分析服务未启动"消息 + 诊断一句 |

## 测试

**单元（不依赖 astrbot、不依赖网络）**

- `resolve()` 矩阵：非本机短路；health 通 → `reuse`；`install_path` 有效/无效；PATH 多候选（用户级 shim 被跳过、`.venv` 结构被采纳）；全空 → `bootstrap`/`none`

- 配置写出：临时目录 + 假 provider 数据 → 断言 YAML 的 `llm` 段与 `api.port`
- 幂等：`instance/` 已存在时跳过 clone/安装

## 已知限制

- AstrBot 被强杀（任务管理器）→ 插件自己拉起的服务会成为孤儿进程；下次启用会走级别 1 复用它（不重启、也不清理）
- PATH 顺序不可控：若 PATH 里同时存在多个可校验安装，取遍历顺序第一个命中
- 国内网络下 clone 与装依赖可能失败；`source_repo_url` 可指向镜像，但**没有内置镜像默认值**
- 自举副本与你 `D:\code\stock_robot` 那份互不共享：配置、`reports/`、缓存都是各自的
- `instance/` 不做自动升级：上游代码更新后需手动删除 `instance/` 重装
