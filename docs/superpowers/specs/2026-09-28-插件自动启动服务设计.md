# AstrBot 插件自动启动服务（含依赖拆分）设计

日期：2026-09-28
承接：`2026-09-18-astrbot插件接入设计.md`（该 spec 第 29 行把"插件懒启动服务"列为 P1 备选，本设计把它提为当期工作，并按 P1 备注的代价逐项处理）

## 背景与目标

现状：插件（`D:\code\astrbot_plugin_stock_robot`）已通过 QQ 实测，可用，但要求用户**自己先把 stock_robot 服务跑起来**（`stock-robot run`），否则所有工具调用都回"分析服务未启动"。

目标：**用户只启动 AstrBot，插件自己把分析服务准备好。**

- 零配置：用户不填路径、不注册 PATH、不手动装依赖
- 已有服务在跑（用户自己启的、systemd 托管的、你本机那份）→ 直接复用，不重复启动、不误杀
- 否则 → **自举**：下载源码、建独立环境、装依赖、写最小配置、启动
- 同一套代码同时支持 Windows 与 Linux
- 只为"自用 + 预留发布"服务，不追求多用户/多实例管理

## 非目标（本期不做）

- 不做本机安装探测：**不读 PATH、不提供路径配置项**（见决策记录）
- 不做自动升级：`instance/` 已存在即跳过下载与安装
- 不做进程守护/崩溃自动重启（调用期兜底已覆盖"挂了再拉起来"）
- 不做系统服务化、开机自启
- 不新增主仓 HTTP 端点；主仓只做依赖拆分与一处 `rag` 子命令的友好提示（见"主仓改造"）
- 不为发布做 GitHub 打包/插件市场提交（沿用上一份 spec 的发布预留章节）

## 决策记录

| 问题 | 结论 | 理由 |
|---|---|---|
| 服务来源 | **复用已在跑的服务；否则自举一份独立副本** | 不读 PATH、不提供路径配置项：用户不会把路径注册进 PATH，且省掉整套平台相关的探测/推导逻辑 |
| 取代码方式 | **httpx 下载源码压缩包**（不依赖 git） | 用户选择；Windows/Linux 同一套代码，无需处理 git 二进制与凭据 |
| 启动命令从哪来 | 插件拼 `run --host <base_url 的 host> --port <端口>`，只暴露 `startup_port` | 用户选择"不填命令、少填配置"；端口与 base_url 不会不一致 |
| 进程生命周期 | **只关自己拉起的** | 复用用户手动启动的实例，避免误杀 |
| 触发时机 | **插件启用时启动 + 调用时兜底** | 启用即就绪；中途挂了/启动失败还能自愈 |
| 自举的 LLM Key | **从 AstrBot 当前 provider 自动写入** | 这是"零配置"的关键；代价是 Key 明文落到插件数据目录（与主仓现有做法一致） |
| 自举触发时机 | 只在**插件启用**时触发，调用时只等待进行中的启动 | 避免"问一句股票就卡十分钟装依赖" |
| 依赖拆分 | **只拆 rag**（chromadb + sentence-transformers） | torch 那 2~3 GB 是 rag 独占；vectorbt/apscheduler 体积小，拆分收益不值当 |
| RAG 依赖的地位 | 移入 `[project.optional-dependencies] rag` | 插件的三个端点（analyze/index/reports）完全不用 RAG；主仓已有 try/except 守卫，代码零改动 |

### 服务来源（两级）

| 级别 | 条件 | 动作 |
|---|---|---|
| 1 | `GET {base_url}/health` 通 | **复用**。不启动、不记 `_owns_process` |
| 2 | `auto_install` 为真 | 确保自举实例（`instance/src` 不存在才下载+安装）→ 启动 → 轮询就绪。记 `_owns_process` |
| 3 | 级别 2 不可用或失败 | 保留失败原因，调用时回现状错误消息 + 诊断一句 |

`base_url` 指向远程主机（非本机）时**只做级别 1**：服务不在本机，插件无从启动。

## 跨平台约定（Windows / Linux）

所有路径用 `pathlib` 拼接，平台差异集中在两个辅助函数里：

| 关注点 | Windows | Linux |
|---|---|---|
| venv 内可执行 | `<venv>/Scripts/stock-robot.exe` | `<venv>/bin/stock-robot` |
| venv 内 python | `<venv>/Scripts/python.exe` | `<venv>/bin/python` |
| 建环境 | 优先 `uv venv <path>`；回退 `sys.executable -m venv <path>` | 同；回退路径在 Debian 系可能因缺 `python3-venv` 失败，错误提示写明 `apt install python3-venv` |
| 装依赖 | `uv pip install --python <venv python> -e ".[<extras>]"`；回退 `<venv python> -m pip install -e ".[<extras>]"`（cwd = `instance/src`） | 同 |
| 起子进程 | `asyncio.create_subprocess_exec` + `creationflags=CREATE_NO_WINDOW`（抑制控制台窗口） | 同接口，无该 flag |
| 终止进程 | `terminate()` 实为硬杀，`kill()` 兜底 | `terminate()` = SIGTERM，uvicorn 优雅退出；超时后 `kill()` |
| 日志路径 | `pathlib` 处理，无平台分支 | 同 |

## 组件与接口

新增两个模块，均**不依赖 astrbot**，可独立单测（与既有 `client.py` 同样的边界）。

### `launcher.py`

```python
class ServiceLauncher:
    def __init__(self, base_url: str, port: int, archive_url: str,
                 extras: str, auto_install: bool, timeout: float,
                 data_dir: Path): ...
    async def ensure_ready(self, allow_install: bool) -> ReadyOutcome
    async def stop(self) -> None                  # 只结束自己拉起的
    @property
    def state(self) -> Literal["idle", "starting", "ready", "failed"]
```

- `ensure_ready` 内部用 `asyncio.Lock` 做**单飞**：并发调用共享同一次启动等待，绝不拉起第二个进程
- `state == "failed"` 时保留失败原因（`ReadyOutcome.reason`），调用期直接复用而不重试安装
- 子进程 stdout/stderr 追加写入 `{plugin_data}/astrbot_plugin_stock_robot/service.log`
- 健康探测（`GET /health`，超时 2s）作为模块级函数，便于单测

### `bootstrap.py`

四个独立步骤，各自可单测、可返回明确失败原因。目录约定：`instance = {plugin_data}/astrbot_plugin_stock_robot/instance/`

1. `download_source(archive_url, instance)` — httpx 流式 GET 压缩包 → 解压到 `instance/src/`（去掉压缩包自带的顶层目录；校验成员路径不逃逸目标目录）；`instance/src` 已存在则跳过
2. `make_env(instance, extras)` — 建 `instance/venv/` 并按上文"跨平台约定"装 `-e ".[<extras>]"`
3. `write_config(instance, provider, port)` — 写 `instance/.stock_robot/config.yaml`：`llm` 段取 AstrBot 当前 provider 的 `provider/model/api_key/base_url`，其余用主仓默认值，`api.port = port`
4. `ensure_instance(...)` — 编排 1~3 + 启动 + 就绪等待；失败用 `logger.warning` 记录原因摘要（插件启用时没有会话上下文，进度只能看 AstrBot 日志页）

### `main.py` 挂钩

| 位置 | 动作 |
|---|---|
| `initialize()` | `asyncio.create_task(launcher.ensure_ready(allow_install=True))`，立即返回，不阻塞插件加载 |
| `_run_analysis()` 入口 | `await launcher.ensure_ready(allow_install=False)`；失败不打断流程，交给 `client` 现有错误路径 |
| `terminate()` | `await launcher.stop()` + 现有 `client.aclose()` |

## 配置项（`_conf_schema.json` 新增 5 项）

| 配置 | 默认 | 说明 |
|---|---|---|
| `startup_port` | 空 → 取 `base_url` 的端口 | 自举实例监听的端口 |
| `startup_timeout_seconds` | 60 | 等服务就绪上限（**不含**下载与安装耗时） |
| `auto_install` | `true` | 关闭则只复用已在跑的服务，绝不下载不装依赖 |
| `bootstrap_extras` | 空 | 自举时装的可选依赖；可选 `rag`（chromadb + sentence-transformers，含 torch，数 GB） |
| `source_archive_url` | 空 → 内置常量 `https://github.com/Arrhenius401/stock_robot/archive/refs/heads/main.zip` | 源码压缩包地址；换镜像或自建托管时填（插件只做无凭据的 GET，私有仓库需自备可匿名访问的 URL） |

## 触发规则与时序

### 插件启用（`initialize`）

1. 立即创建后台任务并返回
2. 后台：health 探测 → 通则结束（复用）；否则 `ensure_instance()`（必要时下载+安装）→ 启动 → 轮询就绪
3. 自举过程中用户提问（工具调用）会走到 `ensure_ready(allow_install=False)`，看到 `state == "starting"` → 等待（最多 `startup_timeout_seconds`），仍不就绪则回错误消息并提示"服务可能在安装中，详见插件日志"

### 工具调用

1. `state == "ready"` → 直接走分析流程（现状不变）
2. `state == "starting"` → 等待进行中的启动
3. `state in ("idle", "failed")` → 先补一次 health 探测：通则复用；不通且 `auto_install` 为真 → **不在调用时下载/安装**，直接回错误
4. 失败消息：现有 `❌ 分析服务未启动（{base_url}），请先运行 stock-robot run` 基础上追加一句诊断（安装中 / 安装失败原因摘要 / 日志路径）

### 插件禁用 / 重载（`terminate`）

- 只结束 `_owns_process` 为真的子进程（`terminate()` → 超时 5 秒后 `kill()`）
- 重载 = 杀自己那份 + 重新探测（若用户手动启动的实例在跑，级别 1 会复用，不受影响）

## 自举细节

- 目录：`instance/` 下 `src/`（源码）、`venv/`（独立环境）；`cwd = instance/` → 生成 `instance/.stock_robot/config.yaml` 与 `instance/reports/`
- 幂等：`instance/src` 存在即跳过下载与安装，只启动
- 压缩包：GitHub 归档 ZIP 自带顶层目录（如 `stock_robot-main/`），解压时剥掉，使 `instance/src/pyproject.toml` 直接成立；下载大小随仓库而定（估几 MB ~ 几十 MB）
- LLM Key：从 AstrBot 当前生效 provider 读取，写入 `instance/.stock_robot/config.yaml`（明文，与主仓现状一致）
- 依赖：默认核心依赖（含 vectorbt、apscheduler），不含 `rag`；`bootstrap_extras=rag` 时才装 RAG
- 耗时预期：核心依赖首次安装数分钟；失败时保留安装器输出最后若干行作为原因摘要

## 主仓改造（依赖拆分）

   - 从 `dependencies` 移除 `chromadb>=0.5`、`sentence-transformers>=3.0`

2. 代码零改动（守卫与懒导入均已就位），仅补一处友好提示：`rag` 子命令缺依赖时提示 `pip install -e ".[rag]"` 而不是裸 `ImportError`

## 错误处理

| 场景 | 处理 | 用户可见 |
|---|---|---|
| `base_url` 非本机 | 只做级别 1 | 现状消息 |
| 压缩包下载失败（网络/404） | 记录状态码与异常摘要 | "分析服务安装失败：{摘要}（详见插件日志）" |
| 解压或建环境失败 | 记录输出尾部 | 同上 |
| 装依赖失败 | 记录安装器输出最后若干行 | 同上 |
| 子进程立即退出（端口占用等） | 读 stderr 尾部 | "分析服务启动失败：{stderr 尾部一行}" |
| 就绪超时 | 记 `startup_timeout_seconds` 与日志路径 | "分析服务启动超时（{n} 秒），详见插件日志" |
| 调用期不触发安装 | 不在调用时下载/装依赖 | "分析服务未就绪（可能在安装中），详见插件日志" |
| 全失败 | 保留原因 | 现状"分析服务未启动"消息 + 诊断一句 |

## 测试

**单元（不依赖 astrbot、不依赖网络）**

- health 探测矩阵：通 → `reuse`；不通 + `auto_install` → 走自举；不通 + `auto_install=false` → `failed`；`base_url` 非本机 → 只探测
- 命令与路径拼装：按平台产出 `Scripts/stock-robot.exe` 与 `bin/stock-robot`（用参数注入平台，而非真的换系统）
- 单飞：并发两次 `ensure_ready` 只产生一个子进程（用假可执行脚本计数）
- `stop()`：只结束自己拉起的；复用场景下不动别人的进程
- 配置写出：临时目录 + 假 provider 数据 → 断言 YAML 的 `llm` 段与 `api.port`
- 幂等：`instance/src` 已存在时跳过下载与安装
- 解压安全：成员路径含 `../` 的恶意压缩包被拒绝

**集成（TEMP 假件，不碰真实环境）**

3. **建环境方式可用性**：AstrBot 环境内 `sys.executable -m venv` 是否可用（uv 建的 venv 默认无 pip 的差异），以及 `uv` 二进制是否在 PATH
4. **冷启动耗时**：服务从进程起到 `/health` 通实测秒数 → 校准 `startup_timeout_seconds` 默认值与文案
5. **子进程终止**：Windows 下 `terminate()` 能否干净结束 uvicorn（含 `kill()` 兜底是否必要）
6. **后台任务存活性**：`initialize()` 里 `create_task` 的启动任务在插件加载完成后能否一直跑到结束
7. **GitHub 归档下载可用性**：本机到 `github.com/.../archive/...zip` 的直连速度与成功率（网络不稳时的实际表现），以及是否需要给 `source_archive_url` 备一个镜像默认值

## 已知限制

- AstrBot 被强杀（任务管理器）→ 插件自己拉起的服务会成为孤儿进程；下次启用会走级别 1 复用它（不重启、也不清理）
- 国内网络下下载源码与装依赖可能失败；`source_archive_url` 可指向镜像，但**没有内置镜像默认值**
- 只支持公开可匿名下载的归档 URL（插件不发凭据），私有仓库需自建带鉴权的下载地址
- 自举副本与你 `D:\code\stock_robot` 那份互不共享：配置、`reports/`、缓存都是各自的
- `instance/` 不做自动升级：上游代码更新后需手动删除 `instance/` 重装
- Linux 路径未在真实机器上验证（本机为 Windows），验收需在目标机补跑
