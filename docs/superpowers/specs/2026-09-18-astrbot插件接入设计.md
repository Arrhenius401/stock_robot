# AstrBot 插件接入设计（QQ 股票分析）

日期：2026-09-18
关联：新建独立仓库 `astrbot_plugin_stock_robot`（插件不在本仓实现，本仓零改动）

## 背景

项目最初的设想是让 agent 接入 QQ。接触 AstrBot 后确定以 AstrBot 为接入载体：**对话与 agent 能力完全来自 AstrBot 自身**（其 LLM 工具调用循环、会话上下文、QQ 适配器），本设计要做的是把 stock_robot 的股票分析能力封装成 AstrBot 的 LLM 工具（`@filter.llm_tool`），让 AstrBot 的 agent 在需要时调用。

现有资产决定了这是一次薄接入而非重造：

- stock_robot 已是常驻 FastAPI 服务（`stock-robot run`），提供 `POST /api/v1/analyze`、`POST /api/v1/index`（结构化 JSON 并落盘报告）与报告库查询接口；
- 落盘的 Markdown 报告已是全中文内容（五维指标表、AI 解读、风险、免责声明），插件只需取回并渲染为图片。

## 目标与非目标

### 目标

1. QQ 里通过 AstrBot 的对话 agent 完成个股/指数分析；完整报告由插件渲染为图片**直接发送**到 QQ（另有进度、错误等简短文字消息），不经过 AstrBot 的 LLM 转述。
2. 主仓 stock_robot 零改动（不新增接口、不改响应字段）。
3. 插件依赖最小（httpx），配置可改，仓库形状即 AstrBot 插件市场标准形状，为将来发布预留。

### 非目标

- 不把 stock_robot 自身的 agent（Planner/ReAct/会话管理）搬进 AstrBot；多轮对话、上下文、QQ 会话隔离全部由 AstrBot 负责。
- 本期不暴露研报检索（rag_search）与选股（screen_stocks）——主仓没有对应 HTTP 接口。
- 不做股票名称→代码解析（需要 6 位代码）；不做自定义报告图片模板——渲染复用 AstrBot 内置 `self.text_to_image()` 与全局 t2i 策略/模板配置。
- 不加固定指令处理器（如 `/分析 600519`），仅 agent 工具形态。
- 插件不负责启动/守护 stock_robot 服务：服务须由用户自行常驻运行（README 说明，建议加入 Windows 启动项）；"插件懒启动服务"列为 P1 备选，见决策记录。
- 不改造主仓 CLI、依赖与打包。

## 决策记录

| 方案 | 结论 | 原因 |
|---|---|---|
| **独立插件仓 + HTTP 桥** | **采用** | AstrBot 插件硬约定"仓库根 = 插件根"，与主仓 src 多包布局冲突；重依赖（akshare/vectorbt/chromadb/langgraph）不进入 AstrBot 环境，规避包名污染与依赖冲突；HTTP 面现成且足够（分析、报告库、下载三个端点齐备）；独立仓天然满足发布形状 |
| 同仓适配 | 不采用 | 发布时必须拆仓；插件文件混入主仓会搅乱 lint/test/提交边界 |
| 独立仓 + 子进程桥 | 备选 | 需给主仓补机器可读入口、每次调用冷启动慢；适合将来发布给"不想常驻服务"的用户 |
| 不用插件、AstrBot 直连 MCP server | 不采用 | AstrBot 支持 MCP 工具接入，但配置体验、消息渲染、发布能力均弱于插件 |
| 插件懒启动服务 | P1 备选 | 调用前探测 `base_url`，不可达且配置了 stock-robot 可执行路径时用 `asyncio` 子进程拉起并轮询 `/health` 等就绪；体验为"只启动 AstrBot 即可"。代价是进程生命周期管理（孤儿进程、端口冲突、重复实例）与一类新失败模式，需专门测试 |

## 架构

### 仓库与安装

新仓 `D:\code\astrbot_plugin_stock_robot`，标准 AstrBot 插件结构：

```
astrbot_plugin_stock_robot/
├── main.py              # Star 类、两个 llm_tool、消息编排、插件生命周期
├── client.py            # stock_robot HTTP 客户端（分析调用、报告定位/下载、错误分类）
├── metadata.yaml        # 插件元数据
├── _conf_schema.json    # WebUI 配置 schema
├── requirements.txt     # httpx
├── tests/
└── README.md
```

插件生命周期：`__init__` 创建 httpx `AsyncClient` 供复用；实现 `terminate()`，在插件卸载/停用时关闭客户端（AstrBot 生命周期钩子）。

开发期用目录联接（junction）装进 AstrBot：

```
mklink /J "D:\code\AstrBot\data\plugins\astrbot_plugin_stock_robot" "D:\code\astrbot_plugin_stock_robot"
```

### 数据流

```
QQ 用户消息
  → AstrBot LLM（自行决定调用插件工具）
  → 插件 llm_tool handler
      1. yield 进度消息（直接到 QQ）
      2. httpx POST http://127.0.0.1:<port>/api/v1/analyze（失败则 yield 错误消息后返回）
      3. 拉取最新报告 Markdown（报告库列表取 id → download）
      4. self.text_to_image(markdown) → yield 报告图片（直接到 QQ）
      5. return 一句说明（进入 LLM 下轮 prompt）
  → AstrBot LLM 看到 return 内容，一句话收尾
```

插件无状态：每次调用独立、参数自带 symbol；多轮追问由 AstrBot 的 LLM 与上下文处理。

运行形态：AstrBot 与 stock_robot 服务运行在同一台机器（本设计假设，自用场景）。**服务由用户启动并保持运行**（`stock-robot run`，建议加入 Windows 启动项开机自启）；插件不做进程管理，服务不可达时按错误处理表提示用户启动。

## 详细设计

### 配置（_conf_schema.json）

插件通过 `__init__(self, context: Context, config: AstrBotConfig)` 注入的 `config` 读取以下键（AstrBot 在存在 `_conf_schema.json` 时自动注入，见上表契约）。

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `base_url` | string | `http://127.0.0.1:25618` | 插件调用分析服务的地址 |
| `web_url` | string | 空（回退 `base_url`） | 图片渲染失败时兜底链接的基址。手机访问需填局域网地址，如 `http://192.168.x.x:8765` |
| `timeout_seconds` | int | `100` | HTTP 超时上限；运行时按超时链收敛（见「超时与性能」），非最终生效值 |

schema 版本升级时 AstrBot 自动迁移配置（补默认值、移除废弃键），发布后演进无需用户手工改配置。

### 工具注册方式

采用装饰器 `@filter.llm_tool(name=...)`。docstring 的 `Args:` 段严格按 `参数名(类型): 描述` 编写——官方文档明确警告：装饰器只解析 docstring、不读类型注解，`Args:` 缺失会让参数 schema 为空、LLM 传入的参数被静默丢弃。实现时用单测断言生成的工具 schema 非空，联调验证参数传递。备选路径（记录）：`@dataclass FunctionTool` + `context.add_llm_tools()` 可显式控制 JSON Schema（与主仓 ToolProtocol 风格一致），本期两个单参数工具用装饰器足够。

### analyze_stock 工具

工具签名：`analyze_stock(symbol: string)`；docstring 写明"当用户询问某只 A 股个股的分析、评价、是否值得关注/买入时使用；symbol 为 6 位股票代码（如 600519）"。

执行时序：

1. `yield event.plain_result("⏳ 正在分析 {symbol}…首次分析约需 30~90 秒，请稍等")`
2. `client.analyze_stock(symbol)` → `POST /api/v1/analyze`，超时 `timeout_seconds`（响应仅用于判定成功/失败与提取错误信息，不做字段编排）
3. 拉取本报告的 Markdown：`GET /api/v1/reports?type=stock&query={symbol}` 取最新一条 `id` → `GET /api/v1/reports/{id}/download`
4. `yield event.image_result(await self.text_to_image(markdown))` → 完整报告图片（见「报告图片」）
5. `return "报告图片已直接发送给用户，请勿重复输出内容，用一句话简短收尾即可"`

结果呈现：**图片 + 简短文字消息**（进度、错误、兜底），不发送要点摘要文本。理由：报告 .md 已含全部信息，图片随 QQ 消息直接显示；放弃文字摘要换取实现显著简化，也让主仓回到零改动（不再需要中文标签映射字段）。

平台约定：aiocqhttp 适配器发送 plain 消息时会对文本首尾 `strip()`（去空格与换行）；插件发送的均为单行短消息，不受影响。

### analyze_index 工具

工具签名：`analyze_index(symbol: string)`；仅支持单指数，docstring 写明"当用户询问大盘/指数（如上证指数、沪深 300、中证 500）走势与估值时使用"。多指数对比是 Web UI 能力（LLM 可连续调用两次）。

时序与个股一致：进度消息 → `POST /api/v1/index`（判定成功/失败）→ 报告定位（`type=index`）→ 下载 .md → 渲染发送图片。指数报告 .md 已含概览、各分面小结与综合定性，无需另行编排文本。

### 报告图片

成功路径的交付物就是一张报告图片。步骤：

1. 定位最新报告：`GET /api/v1/reports?type=stock&query=<代码>`（列表按时间倒序，`reports[0]` 即刚生成的报告，含 `id` 字段；指数用 `type=index`）。
2. 下载 Markdown：`GET /api/v1/reports/{id}/download`（`media_type=text/markdown`）。
3. 渲染：`await self.text_to_image(markdown)`（Star 基类方法，支持 Markdown）→ 图片 URL。渲染策略与模板跟随 AstrBot 全局配置 `t2i_strategy`（默认 `remote`：文本发往 AstrBot 官方 t2i 渲染服务，需外网；`local`：离线 PIL 回退）与 `t2i_active_template`，插件不自定义。
4. 发送：`yield event.image_result(url)`。

失败降级链：定位/下载/渲染任一环节失败 → `logger.warning` + `yield` 一行兜底消息（`❌ 报告图片生成失败，可在 Web UI 报告库查看：{web_url}/#report-library`），流程不中断、不重复分析。

P1（待验证后升级）：若 Web UI 支持 `#report-library/<report_id>` 深链定位，兜底链接升级为直达具体报告；需要改主仓 UI 则不做。

### 错误处理

所有分支都：先 `yield` 一条用户可读消息，再 `return` 一句给 LLM 的说明（避免 LLM 因空结果产生幻觉或重复尝试）。

| 场景 | 用户看到的消息 |
|---|---|
| 连接失败（服务未启动） | `❌ 分析服务未启动（{base_url}），请先运行 stock-robot run` |
| HTTP 422（代码非法） | `❌ 无法识别代码 {symbol}，请提供 6 位股票代码（如 600519）` |
| HTTP 500 | `❌ 分析失败：{error 摘要}` |
| 超时 | `⏱️ 分析超时（超过 {实际生效超时} 秒）。首次分析需拉取数据较慢，可稍后重试或调大插件超时配置` |
| 响应异常（无法判定成功/失败） | `❌ 分析结果异常，已记录日志`（同时 logger 记录完整响应） |
| 报告图片生成失败（定位/下载/渲染） | `❌ 报告图片生成失败，可在 Web UI 报告库查看：{web_url}/#report-library`（分析本身已完成、报告已落盘） |

### 超时与性能（超时链一致性）

超时链分两层，**插件必须始终先于 AstrBot 超时**——AstrBot 超时会直接终止工具，用户只能看到通用错误，不会收到插件的友好提示：

1. AstrBot 工具超时：`provider_settings.tool_call_timeout`（默认 120 秒）。
2. 插件 HTTP 超时：配置 `timeout_seconds`（默认 100 秒），**运行时自动收敛**——每次调用读取 AstrBot 配置（`self.context.get_config(umo=event.unified_msg_origin)` → `provider_settings.tool_call_timeout`），实际生效值 = `min(配置值, tool_call_timeout − 15)`；15 秒边际覆盖解析与消息发送耗时。读取失败则回退配置值并 `logger.warning`。

进度消息与超时错误消息均写出本次实际生效的超时值，便于排查。README 说明该链条，建议 `tool_call_timeout ≥ 120`。

- 首次（缓存冷）分析可能 60~90 秒：akshare 首次拉取数据。进度消息先行发送缓解等待焦虑。
- 同一次分析结论以本机服务端缓存为准；插件不做缓存。
- 报告图片段（报告定位 + 下载 + 渲染）在分析 HTTP 段之后独立计时（AstrBot 超时按每个 yield 段分别计时），通常数秒；`remote` 策略单次渲染超过 3 秒时 AstrBot 会输出告警（官方行为），不影响本次发送。

## 测试策略

1. `client.py` 单测（respx mock httpx）：分析 200 正常、422/500 错误分类、超时、连接失败；报告定位（列表含 `id`、空列表）与报告下载（200/404）各返回结构化结果。
2. 降级逻辑单测：图片链任一环节失败 → 产出兜底消息文案（含 `web_url`），流程不抛出。
3. 工具 handler 保持"薄包装"：只做 yield/return 编排，业务逻辑在 client 与可测辅助函数内，单测不触碰 AstrBot 类型。
4. 手工联调验收（真实 AstrBot + 真实 stock_robot 服务 + QQ）：
   - 插件在 AstrBot WebUI 正常加载、配置可改（代码改动后用 WebUI「重载插件」热重载）
   - QQ 说"帮我看看贵州茅台" → 进度消息 → 报告图片 → LLM 一句收尾
   - 图片内容与 Web UI 报告一致、手机可读（含 Markdown 表格）
   - 指数路径同样出图
   - 停掉服务 → 收到"服务未启动"提示；无效代码 → 收到代码提示；超时 → 收到超时提示
   - 模拟图片链失败（如临时断外网触发 remote 渲染失败）→ 收到兜底链接消息

## 待验证项（实现阶段先探针）

1. `yield event.plain_result` / `event.image_result` 直发路径在真实运行中的行为（消息到达 QQ、无重复发送、`tool_direct_result` 无副作用）——源码已确认链路，运行验证仍必须。
2. 用户 AstrBot 配置中 `provider_settings.tool_call_timeout` 实际值（本机已确认 120），以及写进 README 的建议值。
3. 超时收敛实测：调整 AstrBot `tool_call_timeout` 为不同值，确认插件实际 HTTP 超时随之收敛，且插件超时消息先于 AstrBot 终止到达用户。
4. 报告图片渲染实测：`text_to_image` 渲染完整报告（含 Markdown 表格）的效果与图片高度；长图在 QQ 手机客户端的显示；`remote` 策略的外网可用性与单次耗时；`local` 策略样式对比（用于 README 建议）。
5. 本机 AstrBot `t2i=false`（自动转图开关关闭）时，插件主动调用 `self.text_to_image()` 预期不受该开关影响（该开关只控制自动转换）——运行验证确认。
6. 报告库深链能力探针（决定兜底链接是否升级为 P1 深链）。
