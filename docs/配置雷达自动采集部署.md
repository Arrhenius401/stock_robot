# 配置雷达独立采集服务部署

日期：2026-09-30

## 运行方式与数据

浏览器和 Web 服务负责保存计划、发起人工请求与查询状态，独立采集进程负责执行。关闭浏览器或重启 Web 不会取消任务。自动开关关闭后，采集进程仍待命，人工采集与有限重试可以使用。

自动计划默认每天北京时间 18:30。服务使用上市市场交易日历，恢复时只发布最近已闭市交易日，补齐已声明行情覆盖范围内的缺失日线。成功项重试复用已验证缓存，失败项有限重试，最多三次。新池默认启用；关闭池不进入自动范围。

数据沿用项目 `.stock_robot` 目录中的 `radar.db`、`radar_collector.db`；没有带 `_v2` 的新数据库。旧状态审计与已完成快照保留。SQLite 文件应位于可由服务账户写入的本地磁盘。复制整个项目时不要把密钥和生产数据库放进 Git。

所有系统启动入口都使用项目中 `scripts/run-radar-collector.py` 的绝对路径。脚本固定项目 `src` 和工作目录，避免其他全局安装或 editable 安装选错源码。

## Windows 本地运行

在当前用户登录后运行，无需尚未登录时采集。系统任务名为 `StockRobotRadarCollector-<项目指纹>`，项目路径不同则任务名不同。任务采用当前用户、最低权限、忽略重复实例，不受空闲或电池条件影响。

Windows 任务通过 `--supervise` 保持一个采集子进程；子进程非零退出后等待 15 秒再启动，正常退出不会重启。监督进程使用 Windows Job Object，系统任务停止时一并回收采集子进程及其后代。Linux 仍由 systemd 重启，不使用该监督模式。

配置入口启用登录启动后注册并请求立即运行；注册成功不能当作服务在线，仍以当前采集进程的新心跳为准。关闭登录启动只禁用任务，正在运行的服务仍可工作；关闭自动计划只改变任务库里的业务开关。

从项目根手动运行：

```powershell
.\.venv\Scripts\python.exe .\scripts\run-radar-collector.py radar daemon
```

查看状态、执行人工单次采集：

```powershell
.\.venv\Scripts\python.exe .\scripts\run-radar-collector.py radar collector-status
.\.venv\Scripts\python.exe .\scripts\run-radar-collector.py radar collect --once
```

人工采集可指定 `--universe cn_hk_etf`；指定历史日期用 `--date YYYY-MM-DD`。后台服务启动受单实例锁控制，重复运行不会产生并行采集。

本期不增加启动目录后备启动器。任务计划程序无权注册时，配置会显示原因，可以使用上述前台命令由登录会话手动托管。

## 旧 Windows 启动项切换

迁移检查旧 `StockRobotRadarCollector` 任务、`stock-robot-radar-collector.cmd` 启动文件以及旧采集进程。只有完整命令确实匹配当前项目 `.venv/Scripts/stock-robot.exe radar collect` 且工作目录可确认属于当前项目时，才禁用任务、删除启动文件或停止进程。其他项目的同名入口不会处理。

停止旧进程前会再次核对 PID 当前命令及工作目录，避免 PID 被其他程序复用或同一虚拟环境被其他 checkout 复用。可选的 psutil 查询库不可用或无权读取目录时不会终止未知进程，迁移会给出人工检查原因。迁移先写项目内 `radar_collector.disabled`，阻止仍在使用旧实现的采集进程再次工作。清理失败返回 `cleanup_pending` 与具体原因；已知旧进程未停止或无法核验进程时还返回 `unsafe_overlap`，新服务应拒绝并行切换，记录到采集审计；保留关闭标记。新独立服务使用任务库开关，不以旧标记决定是否待命。

关闭标记即使完整清理成功也保留，以防用户重新启用仍注册的旧任务。不要手动删库处理迁移问题。

## Linux 长期运行

安装依赖与虚拟环境后，在实际服务器项目目录生成 unit。用普通服务账户，例如 `stockrobot`，不要以 root 运行采集业务进程。

```bash
cd /srv/stock_robot
.venv/bin/python scripts/run-radar-collector.py radar service-unit --user stockrobot --output /tmp/radar-collector.service
```

生成命令会提示实际 unit 名称 `stock-robot-radar-<项目指纹>.service`。把它完整复制给 `collector_unit_name` 后安装；不要使用旧通用任务名。

```bash
collector_unit_name='替换为生成命令提示的完整 service 名称'
sudo install -m 644 /tmp/radar-collector.service "/etc/systemd/system/$collector_unit_name"
sudo systemctl daemon-reload
sudo systemctl enable --now "$collector_unit_name"
systemctl status "$collector_unit_name"
journalctl -u "$collector_unit_name" -n 100 --no-pager
```

unit 固定 `User`、`WorkingDirectory`、虚拟环境 Python 和项目启动脚本，使用 `Restart=on-failure`、15 秒恢复间隔。服务账户需能读取项目代码、配置和虚拟环境，并能写入项目状态目录。

网页在 Linux 仅保存业务计划与查询系统能力，不执行 sudo。系统启动设置由部署人员执行 `systemctl enable` 或 `disable`。不使用 systemd 的环境可用相同 `radar daemon` 前台命令交由已有进程管理器托管，配置页应显示实际心跳与可用管理能力。

## 排查顺序

1. 用 `radar collector-status` 确认业务开关、设置时间及最近心跳。
2. 查看采集记录中的阶段、失败原因和项级结果；不要用启动文件是否存在判断在线。
3. 日历无有效覆盖时服务停止自动计划并显示错误，不会猜测工作日。已有覆盖的缓存可在网络失败时沿用。
4. 行情未到目标日、内部缺口或无效价格时该项失败，不会把旧数据声明为 fresh；上一次健康快照继续可读。
5. 同日已成功任务按池和配置指纹跳过；终态失败需人工重试或新的目标/配置，不会在每轮轮询反复入队。
