# 升级与版本维护

## 统一元信息

应用发布版本只手工修改 `src/stock_robot/metadata.py` 的 `VERSION`。setuptools 静态读取该值，CLI `--version`、HTTP `/health`、OpenAPI、MCP 默认身份与回测产物版本均引用它，不读取其他环境可能遗留的旧安装元数据。

同文件维护展示名 `APP_NAME` 和公共标识 `DISTRIBUTION_NAME`。后者是稳定项目身份，不能作为一次普通发版改名；Python 打包规范仍要求 `pyproject.toml` 声明项目名称，两者需保持一致。

运行默认值仍集中在 `src/utils/config.py` 的 `DEFAULT_CONFIG`，CLI 显式参数 > 用户配置 > 默认值；现有 `.stock_robot/config.yaml` 不被新默认值覆盖。密钥不属于发布元信息，禁止写入该文件。

MCP 协议、策略、数据格式与静态资源缓存版本各有兼容含义，不随应用版本同步修改。更新日志中的历史版本也不由当前版本替换。

## 构建与验证

开发环境先运行 `scripts/bootstrap-dev.ps1` 同步开发与构建工具。改版本后使用 `uv lock` 更新动态元数据；依赖变更后重新生成安装清单：

```sh
uv lock
uv export --frozen --no-dev --no-emit-project --format requirements.txt --output-file requirements-core.lock.txt
uv export --frozen --no-dev --no-emit-project --extra rag --format requirements.txt --output-file requirements-rag.lock.txt
```

Windows 可将 `UV_CACHE_DIR` 环境变量设为仓库 `tmp/uv-cache`，避免依赖用户目录缓存权限；不要把机器绝对路径写进生成命令。业务依赖没有改变时，导出清单应保持内容不变。

普通检查用 `scripts/verify.ps1 -Scope Changed`；发布前必须显式 `-Scope Full`。`tests/test_distribution.py` 从声明的干净源码构建 sdist/wheel，再从 sdist 重建、安装 wheel 并运行离线冒烟。它只复用测试环境的第三方依赖，不读取父环境 editable 路径，因此不能替代目标 Linux 的全新依赖下载／安装验收。

构建钩子 `src/stock_robot/_build.py` 将根目录 config、白名单 data 和采集脚本复制进包内；模板、静态页面和分析 YAML 使用 package-data。不要手工维护第二份资源，也不要向安装包加入本地配置、报告、候选映射或缓存。

## 已部署主仓的手动升级

以下适用于手动维护的服务。**插件自举实例不要在插件运行时直接替换源码或虚拟环境**，应走插件的受管升级与回退流程；新版插件本身也需要独立验收。

1. 记录当前源码提交／标签、CLI 版本、启动方式、Python 环境与服务工作目录。记录是否启用 `rag`，新版本沿用相同能力，不混用系统 Python 或其他项目 venv。
2. 停止 Web、分析任务和独立雷达采集进程。对当前工作目录 `.stock_robot/`、`reports/` 以及人工修改过的根 `config/`、`data/` 做完整备份。SQLite 文件要在相关进程停止后复制，避免数据库与 WAL 不一致。备份可能包含 API Key，只存放在受限目录，不上传到仓库或聊天。
3. 下载明确版本到新目录，建立新的虚拟环境；不要直接覆盖旧安装，也不要仅运行 `git pull` 后复用未知依赖状态。安装锁定业务依赖，再 editable 安装源码。以 Linux core 为例：

   ```sh
   python3 -m venv /srv/stock-robot-candidate/venv
   /srv/stock-robot-candidate/venv/bin/python -m pip install --require-hashes -r /srv/stock-robot-candidate/src/requirements-core.lock.txt
   /srv/stock-robot-candidate/venv/bin/python -m pip install --no-deps -e /srv/stock-robot-candidate/src
   /srv/stock-robot-candidate/venv/bin/stock-robot --version
   ```

   开启知识库时换用 `requirements-rag.lock.txt`，不要先装 core 再让 pip 自由解析 rag。Windows 使用对应候选环境的 `Scripts/python.exe` 与 `Scripts/stock-robot.exe`。

4. 在隔离工作目录放入备份副本，使用备用本机端口启动候选服务。先核对 CLI、健康接口版本一致，再查看页面、历史报告与数据库兼容性；按需做一次实际分析。只对数据副本测试，避免旧版本回退时面对新版本已经修改过的原数据库。测试环境禁用订阅推送和雷达自动采集，防止重复任务。
5. 验证通过后停止候选，切换原服务的可执行文件到新环境，**保持正式工作目录不变**。启动并再次验证。源码安装继续使用其 config/data；如有人工修改，逐项核对后合并，不能整目录覆盖新版本默认值。
6. 失败时停止候选／新服务，切回旧可执行文件和旧源码；必要时还原停服备份的配置与数据库。保留旧环境直至实际业务确认正常，不在验收前删除它。

## wheel 与源码模式

wheel 将默认资源放在安装包内，配置、缓存、报告仍属于用户运行目录。wheel 的行业映射更新使用 `.stock_robot/data/industry_mapping.csv`，第一次写入时从内置数据创建副本，后续查询优先使用该副本。不要直接编辑 `site-packages`。

源码模式保留原有根目录 config/data 与更新方式。不同安装模式间切换时需核对人工更新的映射，不会自动将用户数据搬入包内。雷达现有源码产物路径保持兼容；wheel 的雷达产物和采集工作目录使用运行目录。

正式发布前还须核验目标服务器的 Python、平台依赖和真实升级流程；主仓安装冒烟不能替代 QQ 平台、AI 回复、报告图片权限或群聊队列验收。
